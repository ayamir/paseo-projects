# OVNFS 接入方向与生命周期讨论

状态：领域模型与接入方向已确认，领域建模讨论已完成。Q1–Q20、整体模型及分阶段接入方向均经用户确认，不表示已经实施或通过验收。本文件不授权合并回滚 PR、部署后端切换、停止现有 Agent 或删除历史数据。

术语见 [GLOSSARY.md](../GLOSSARY.md)。

## 已确认

### Q1：接入目标

OVNFS 最终成为 PP 默认使用的隔离工作副本后端。Git worktree 在过渡期间保留，是否最终移除由验证结果决定。

切换时机取决于依赖复用、运行稳定性、恢复与回收等验收结果；具体门槛尚未确定。

### Q2：管理范围

用于 PP 任务的所有工作副本，以及 Agent 创建的相关实验副本和快照，都必须登记到 PP。PP 负责记录归属并管理生命周期。

Agent 可以申请创建和保留。用户在 PP 之外创建的目录，必须明确接管后才纳入管理。

### Q3：任务与资源分别结算

线程完成与工作副本回收分别表达。线程可以完成，而工作副本仍等待归档、释放占用，或处于明确保留、回收失败状态。

尚未回收的资源必须能被看见，能说明原因，并支持后续跟进与重试。具体状态集合和状态转移尚未确定。

### Q4：单一归属与跨线程派生

每个可独立回收的工作副本只有一个所属线程；线程可以拥有多个实验副本和快照。跨线程接续工作时创建派生副本，避免共同修改同一个环境。

底层存储可以共享，但不能混淆工作副本归属。结束原线程不能破坏另一线程的派生环境。

### Q5：成果与现场分离

提交、报告和明确登记的产物构成需要保存的成果。完整工作副本作为执行现场，默认不要求永久保留；确需完整环境才能重现的实验可以申请保留现场。

独有提交、未提交修改或无法判断用途的文件必须先确认去向，不能直接视作可删除内容。具体保存证明尚未确定。

### Q6：保留申请与解除

Agent 申请保留必须提供理由，以及到期时间或可验证的解除条件。只有用户可以明确决定长期保留。

解除保留只代表允许进入回收检查，不代表可以直接删除。独有数据或进程占用等阻碍仍须处理，并显示保留原因。

### Q7：完成后默认自动回收

线程完成后，PP 自动启动归档与回收流程。所有检查通过且没有有效保留要求时直接回收，无需逐个向用户确认。

同一线程的多个资源分别检查；符合条件的先回收，存在阻碍的保留并显示原因，不要求所有资源一起等待。

修订（2026-11-24）：OVNFS 副本暂不自动回收。固定版本的 `rm` 没有身份、写入和占用保护，检查到删除之间的空档由人担保：通过全部检查的副本列为候选，用户在终端用 `pp sweep` 批量确认。上游提供带条件的删除后再恢复自动回收。

### Q8：成果保存必须有可恢复证明

成果必须存在于工作副本之外，经过验证且能够恢复。判断标准是回收当前工作副本后仍可恢复，而非必须先合并或上传。

代码可以保存在目标仓库或可恢复的独立归档中。报告和登记的产物也必须验证。Agent 口头声明、仅存在于副本内的提交、依赖原副本才能使用的快照以及未经验证的复制，不能单独作为删除依据。

无法判断用途的文件仍须确认处理方式；备份完成不等于自动获得删除许可。

### Q9：持续跟进与安全重试

回收失败、进程仍占用或保留条件未解除时，PP 持续记录原因，在条件变化或重启恢复后自动重试。

自动重试不升级为强制删除或强制结束进程，也不跳过保存与归属检查。持续异常需要可见且避免反复通知。

### Q10：统一创建入口与未登记资源

Agent 创建实验副本、快照或派生环境时统一向 PP 申请，由 PP 登记归属并调用后端创建。

绕过 PP 创建的资源显示为未登记、待确认。发现资源不代表取得管理权，不能据此直接接管或删除。

### Q11：依赖保护与底层释放

结束线程只释放其自身资源，不能破坏其他线程或有效快照仍依赖的数据。归属与依赖分别判断。

底层共享数据由后端依据依赖关系释放；PP 不得直接删除底层存储目录以绕过后端机制。无法确认是否影响其他资源时暂停回收并说明原因。

### Q12：中断恢复与真实状态

创建、重启与回收必须支持中断后恢复。部分成功应记录真实状态，不能把失败当作完成。

创建副本成功但 Agent 启动失败时，保留可重试或回收的环境记录。重启后原环境未恢复时，Agent 等待或报错，不得误在源仓库或其他目录继续执行。

恢复操作必须先确认资源身份和实际状态。

### Q13：首批支持范围

第一阶段先完成本机 macOS 的创建、实验、恢复与回收，并限定经过验证的 OVNFS 版本。远程机器、Linux 和 Windows 暂时继续使用 Git worktree。

目标仍是最终替代；先完成一个能够长期使用的完整场景，再扩大覆盖范围。

### Q14：默认策略与显式指定的回退

将来启用 OVNFS 优先策略后，预检确认不可用且尚未创建资源时，可以回退 Git worktree，但必须显示原因和实际后端。

显式指定 OVNFS 时，不满足条件直接报错。一旦资源已经创建或运行，故障进入原资源的恢复流程，不得自动换后端继续执行。

### Q15：明确分类后才自动丢弃

只有明确登记为可重建缓存或可丢弃临时数据的内容，才按规则直接回收。被 Git 忽略、位于 TEMP 或目录名称为 node_modules 均不足以单独构成分类依据。

用途不明确的内容作为可见的回收阻碍，允许用户补充分类；分类明确后可减少后续同类任务的人工介入。规则的适用范围与验证方法仍须细化。

### Q16：资源压力不降低数据保护标准

达到资源预算或磁盘空间警戒线后，暂停创建新的副本和快照。已有任务尽可能继续运行，仅回收已经满足条件的资源，不擅自解除保留或删除未知数据。

阻碍与可采取的操作必须可见。具体预算与警戒线结合后续测量确定。

### Q17：默认后端切换的两类验收

先通过生命周期与恢复验收，再通过与 Git worktree 的实际收益对照，才将 OVNFS 提升为默认后端。

生命周期验收覆盖中断恢复、独有数据保护、跨线程派生、归档验证和回收。收益对照使用相同任务，比较环境准备时间、执行表现和存储占用，并区分逻辑大小与实际物理占用。

生命周期可靠但收益尚未证明时，可以继续作为可选后端。不能仅凭支持 COW 推断更省空间或更快。可靠性决定能否使用，实测收益决定是否值得成为默认。

### Q18：历史线程保持原后端

现有线程不原地转换后端。新规则先用于新建资源，旧线程继续使用原环境，经过核对后逐步纳入管理和回收。

历史副本须核对归属、成果与依赖，未登记资源先等待认领。不能仅凭线程已 resolved 批量删除目录。接受过渡期间同时管理两种后端，以及历史遗留逐步收敛。

### Q19：明确的代码基线

新线程默认使用明确的提交版本，不自动继承源目录中的未提交修改。继续已有实验时从已登记的工作副本派生，并记录实际起点。

需要带入用户尚未提交的修改时必须显式选择，并将这些修改纳入可恢复的起点记录，以区分原有变化和线程产生的变化。

### Q20：受项目规则约束的环境复用

项目明确声明允许继承和复用的内容。未知的 Git 忽略文件、凭据和本机状态不默认带入。

复用后各线程写入必须相互隔离；影响缓存有效性的输入发生变化时必须重新验证或重建。不满足规则时重新准备环境，而不是复用可能失效的缓存。

接受初次接入项目时建立复用规则的成本，以确保环境正确、来源明确。

## 已确认的整体模型

Q1–Q20 已逐项确认，以下整体模型也已完成最终一致性确认。它是后续规格与实现的设计依据，不是已部署能力说明或实现授权。

### 领域对象与关系

- 项目承载任务上下文、环境复用规则和资源预算。
- 线程记录一次委派工作及其结果。一个线程可以拥有多个工作副本和快照，线程完成不代表资源已经回收。
- 会话是 Agent 的执行与对话上下文，与线程记录、工作副本分别管理；停止会话不等于回收环境。
- 工作副本是执行环境。每个可独立回收的工作副本只有一个所属线程，使用明确的代码基线。
- 快照保存某个工作副本的时点状态；是否独立可恢复必须另行验证，不能仅凭存在快照认定成果已归档。
- 派生副本承接已登记环境的状态，具有自己的归属和写入隔离；来源及依赖需要保留，以免回收原资源时破坏派生资源。
- 交付成果是需要保存的提交、报告和登记产物。其保存证明独立于工作副本是否仍存在。
- 现场保留暂缓回收。Agent 申请保留须有理由与期限或可验证的解除条件，用户可以决定长期保留。
- 后端提供工作副本与相关资源的具体能力。PP 管理归属、流程与证据，后端处理其掌握的底层共享依赖和数据释放。

物理路径、界面中的工作区和工作副本的领域身份不能混为一谈。恢复与回收须依据可验证的资源身份，不能仅凭路径存在或目录名称。

### 生命周期与回收条件

建议用两个维度表达资源，而不是把全部情况塞进一个 complete 标记：

1. 生命周期阶段：申请、创建中、可用或使用中、结束使用待归档、待回收、回收中、已回收。创建和其他操作部分成功时另记真实操作结果，支持恢复。
2. 当前阻碍：身份或状态未确认、成果未验证、未知文件未分类、进程占用、保留生效、依赖不明、后端操作失败。阻碍可同时存在，需可见且可重试。

这些是领域阶段与阻碍的示意，具体存储字段和状态名称尚未定稿。

正常流程为：

1. PP 登记归属、基线和创建意图，再通过后端创建资源。
2. 资源身份及实际状态确认后，允许 Agent 使用；实验副本、快照和跨线程派生仍通过 PP 创建。
3. 线程完成后，各资源分别进入归档与回收检查。
4. 成果在该工作副本之外得到验证，未知内容已明确处置；同时不存在有效保留、进程占用或依赖风险，才允许后端回收。
5. 验证回收结果后标记已回收。底层共享数据的实际释放由后端处理，不能把逻辑资源回收等同于已释放相同数量的物理空间。
6. 任一步失败均保留真实状态和原因，在条件变化或重启恢复后重试；不强制杀进程、不自动强删、不改到其他目录继续执行。

### 关键边界场景

- 副本创建成功但 Agent 启动失败：保留环境记录，后续重试启动或按规则回收，不能留下不可见资源。
- 线程已经完成但验证进程仍运行：线程保持完成，资源显示占用；进程退出后重新检查，不强制结束进程。
- 另一个线程使用派生副本：原线程完成不影响派生副本；无法确认共享依赖安全时暂停回收。
- 报告复制成功但不能验证，或仅有依赖原环境的快照：不得认定成果已安全保存。
- 机器重启后挂载未恢复：等待或报错，不能将相同路径当作普通目录使用，也不能换到源仓库继续运行。
- 发现未登记的实验环境：显示待确认，不因名称类似或线程已结束就自动接管、删除。
- 磁盘空间不足：限制新副本和快照，尽量维持已有任务，只回收已符合条件的资源。
- 未提交修改、未知忽略文件和凭据：不隐式带入新环境；明确选择的修改须形成可恢复起点，允许复用的内容受项目规则约束。

### 已确认的分阶段接入方向

以下阶段划分已随整体模型确认，具体实施尚未授权执行：

1. 完善共同的资源模型：登记、归属、状态、保留、归档证据、恢复与回收重试。Git worktree 暂留默认，避免把共同的生命周期问题留给某个后端独自处理。
2. 完成本机 macOS 的 OVNFS 可选闭环：限定验证版本，覆盖主副本、实验、快照、派生、会话恢复与回收；所有创建走 PP，环境复用受项目规则约束。
3. 核对并逐步纳管历史资源：旧线程保留原后端，不原地转换；未知资源先认领，独有成果先保存，不批量删除。
4. 进行完整场景和故障恢复验收，并与 Git worktree 做同任务对照。生命周期可靠但收益未证明时继续保持可选。
5. 验收满足后逐步提升为默认：按 Q14 处理创建前回退，按 Q13 扩展支持范围。是否最终移除 Git worktree 继续依据验证结果决定。
