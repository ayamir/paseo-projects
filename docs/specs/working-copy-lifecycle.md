# PP 工作副本生命周期与 OVNFS 接入规格

状态：规格及测试边界均已确认，已发布为 [GitHub issue #7](https://github.com/ayamir/paseo-projects/issues/7)，标签为 `ready-for-agent`。发布规格不触发实施、部署或历史资源删除。

依据：[已确认的设计决策](../ovnfs-design.md)及[领域词汇表](../../GLOSSARY.md)。本规格描述目标行为，不代表现有 PP 已具备这些能力。

## Problem Statement

用户将代码工作委派给 PP 的线程后，需要能够判断：任务是否完成、成果是否安全保存、执行环境为什么还存在，以及何时可以释放空间。当前线程完成和环境回收之间缺少完整、持续的管理闭环：保留声明可能没有解除条件，后续重试覆盖不足，额外实验副本或快照可能没有归属，资源被保留时的清理结果仍可能看起来已经完成。

这些问题同时影响 Git worktree 和 OVNFS，不能仅靠切换后端解决。用户既不希望完整执行现场无限积累，也不愿为了释放空间丢失独有提交、实验产物或仍被其他线程使用的数据。

OVNFS 具有复用环境与派生实验的潜在价值，但 PP 尚未证明其在真实任务、故障恢复和存储占用方面足以成为默认后端。用户需要先获得可解释、可恢复的资源管理，再基于相同任务的实测结果逐步切换。

## Solution

由 PP 统一登记和管理用于任务的工作副本、实验副本、快照及派生关系。线程记录工作结果，资源记录自身生命周期；会话停止、线程完成和资源回收分别表达。

每个工作副本只有一个所属线程。跨线程继续实验时创建具有独立写入环境的派生副本，允许后端共享底层存储，但不能共享可变执行现场。成果保存、现场保留和底层存储释放分别验证。

线程完成后自动启动各资源的归档与回收检查。成果在该工作副本之外可恢复，未知内容已明确处置，而且不存在有效保留、进程占用或依赖风险时，自动通过后端回收。否则显示具体阻碍并持续跟进；条件变化或重启后重新核对，不强制删除、杀进程或跳过检查。

先完善两个后端共同的生命周期管理，保持 Git worktree 默认；再完成经过版本验证的本机 macOS OVNFS 闭环。可靠性验收和同任务收益对照均通过后，才逐步提升 OVNFS 为默认后端。

本规格分阶段交付，不以“OVNFS 最终默认”为由，在生命周期与收益尚未验收时提前改变现有默认行为。

## User Stories

1. 作为项目用户，我希望线程完成与资源回收分别显示，以便知道工作已经结束但环境仍在等待什么。
2. 作为项目用户，我希望看到每个工作副本、实验副本和快照的归属，以便追踪空间占用和后续处理责任。
3. 作为 Agent，我希望通过 PP 申请主任务环境，以便创建失败或重启后仍能找到对应记录。
4. 作为 Agent，我希望通过 PP 申请额外实验副本，以便实验环境能够随任务一起被管理。
5. 作为 Agent，我希望通过 PP 创建和登记快照，以便记录实验时点并保护仍有用途的数据。
6. 作为继续其他线程工作的 Agent，我希望创建自己的派生副本，以便承接已有状态而不共同修改同一个环境。
7. 作为项目用户，我希望原线程完成时不会破坏其他线程的派生环境或有效快照，以便并行工作不被回收动作打断。
8. 作为项目用户，我希望新环境从明确的提交版本开始，以便区分原有代码和线程产生的变化。
9. 作为项目用户，我希望源目录的未提交修改不会被隐式带入，以便避免不知情地改变实验基线。
10. 作为项目用户，我希望可以显式带入尚未提交的修改并保存可恢复起点，以便继续当前工作且能够解释环境来源。
11. 作为 Agent，我希望环境准备完成并确认身份后再开始执行，以便不会在错误目录修改代码。
12. 作为项目用户，我希望后端实际选择和回退原因可见，以便判断线程使用了何种环境。
13. 作为显式选择 OVNFS 的用户，我希望其不可用时直接报错，以便指定后端的实验不会静默使用其他机制。
14. 作为使用未来默认优先策略的用户，我希望仅在预检失败且尚未创建资源时允许回退 Git worktree，以便兼顾可用性和环境一致性。
15. 作为项目用户，我希望已创建资源故障后恢复原资源，以便不会悄悄换后端或换目录继续运行。
16. 作为项目用户，我希望副本创建成功但 Agent 启动失败时仍能看到环境，以便重试启动或按规则回收。
17. 作为项目用户，我希望进程或机器中断后保留真实的部分成功状态，以便不会留下不可见资源或重复破坏现场。
18. 作为项目用户，我希望资源身份或挂载尚未恢复时暂停执行，以便 Agent 不会误在源仓库或普通空目录工作。
19. 作为项目用户，我希望报告、提交和登记产物在环境之外得到验证，以便回收后仍可恢复成果。
20. 作为项目用户，我希望只存在于副本内的提交、口头报告和未经验证的复制不能触发删除，以便成果不会因误判而丢失。
21. 作为项目用户，我希望依赖原环境的快照不会被误当作独立归档，以便删除工作副本后仍能得到承诺的恢复能力。
22. 作为项目用户，我希望独有提交、未提交修改和未知文件先明确去向，以便自动回收不替我决定丢弃数据。
23. 作为项目用户，我希望只有明确登记为可重建缓存或可丢弃数据的内容才能自动丢弃，以便 Git 忽略规则或目录名不会成为删除许可。
24. 作为项目用户，我希望可以补充未知内容的分类，以便同类任务后续减少人工介入。
25. 作为 Agent，我希望以明确理由及期限或可验证条件申请保留，以便确有需要的实验现场可以继续存在。
26. 作为项目用户，我希望只有用户能够决定长期保留，以便 Agent 的临时请求不会变成永久占用。
27. 作为项目用户，我希望保留解除后重新执行完整回收检查，以便到期不等于直接删除。
28. 作为项目用户，我希望同一线程中符合条件的资源先被回收，以便一个仍在使用的实验环境不会阻塞全部空间释放。
29. 作为项目用户，我希望进程占用、依赖不明或归档未验证都能显示为具体阻碍，以便采取正确的后续操作。
30. 作为项目用户，我希望条件变化后自动重试且异常通知不反复轰炸，以便无需一直手动追踪。
31. 作为项目用户，我希望自动重试不会强杀进程、强制删除或降低保护标准，以便失败次数不会增加数据风险。
32. 作为项目用户，我希望工作副本经后端回收后再验证结果，以便失败不会被记作成功。
33. 作为项目用户，我希望底层共享数据由后端释放，以便 PP 不会绕过依赖保护直接删除存储目录。
34. 作为项目用户，我希望未登记的环境仅显示为待确认，以便发现目录不会自动赋予 PP 删除权。
35. 作为项目用户，我希望明确接管外部环境后才进入管理流程，以便我自行创建的资源保持原有控制权。
36. 作为项目用户，我希望缓存复用仅包含项目明确允许的内容，以便未知忽略文件、凭据和本机状态不会隐式进入新环境。
37. 作为并行工作的 Agent，我希望复用后各副本的写入相互隔离，以便修改依赖或缓存不会改变其他线程的运行环境。
38. 作为项目用户，我希望影响缓存有效性的输入变化后重新验证或重建，以便提速不会以使用失效环境为代价。
39. 作为项目用户，我希望空间压力时限制新副本和快照而尽量维持已有任务，以便资源预算不会触发未经许可的数据丢弃。
40. 作为项目用户，我希望旧线程继续使用原后端并逐步核对历史资源，以便引入新规则不会原地迁移或批量删除已有环境。
41. 作为项目用户，我希望先验证本机 macOS 的完整闭环，以便后端支持范围明确且经过实际运行证明。
42. 作为远程、Linux 或 Windows 用户，我希望过渡期继续使用 Git worktree，以便本机 OVNFS 接入不会影响现有工作。
43. 作为项目用户，我希望先通过生命周期与恢复验收再比较收益，以便可靠性不足的后端不会因为速度更快而成为默认。
44. 作为项目用户，我希望以同一任务比较准备时间、执行表现和存储占用，以便默认选择有可复核的依据。
45. 作为项目用户，我希望报告区分逻辑大小与实际物理占用，以便 COW 或挂载视图不会导致误导性的空间结论。
46. 作为项目用户，我希望生命周期可靠但收益尚未证明时 OVNFS 继续作为可选项，以便默认切换依据证据而非假设。

## Implementation Decisions

以下为目标契约与实现约束，不固定尚未验证的存储格式、命令名称或具体字段名。

1. **统一资源管理，分离工作与执行环境。** 在线程和会话之外，登记可独立管理的资源。每个工作副本有单一线程归属；主副本、实验副本、快照及派生关系均可追踪。线程状态不能替代资源的归档或回收结果。
2. **公共入口。** PP 的命令入口、Agent 使用入口和现有看板数据读取应共享同一套资源记录与操作契约。增加实验、快照、派生、保留、接管和回收能力，不要求为每个调用方实现不同规则。调用方式和命令命名在实现时确定。
3. **先登记再创建。** 创建意图、归属和明确的代码基线必须在调用后端前形成可恢复记录；部分成功记录实际已创建的资源。重试需要重新核对实际状态，不能重复创建未登记副本。
4. **资源身份独立于路径。** 保存并验证足以区分具体后端资源的身份、位置、来源及实际状态。路径存在、名称相同或界面中的工作区存在均不能单独证明资源身份。身份、状态或挂载无法确认时停止相关执行与回收。
5. **明确代码基线。** 默认以明确提交版本创建。显式继承未提交修改时，应记录并保存可恢复的起点；派生环境记录实际来源及派生起点，不把包含改动的环境表述为未经修改的某个提交。
6. **后端能力边界。** Git worktree 与 OVNFS 接入共同的登记、恢复和回收流程。后端负责创建、识别、检查、恢复及回收具体资源，并对自身共享数据的释放负责。尚不支持某项能力时必须明确报错，不以近似操作冒充成功。
7. **生命周期与阻碍分别表达。** 对外呈现申请、创建、使用、结束使用、归档检查、回收及回收结果；同时允许多个阻碍存在。资源保留、操作失败或状态未知时，不使用一个含糊的 complete 值表示全流程结束。具体状态枚举和记录格式由实现设计确定。
8. **记录足够的恢复信息。** 持久化内容必须能够表达归属、来源与依赖、代码基线、实际后端及身份、阶段、阻碍、保留约束、成果证据和未完成操作。旧线程与新资源记录兼容读取；不能靠改写旧后端类型完成迁移。
9. **完成后按资源推进。** 线程完成触发资源检查；符合条件的资源分别回收。Agent 停止与线程完成不互相冒充；归档 Agent 或关闭界面工作区也不能单独作为文件已安全回收的证明。
10. **成果证据。** 接受工作副本之外、经验证且能够恢复的目标仓库或独立归档，不强制要求先合并或上传。验证应覆盖需要保存的提交、报告和登记产物，并避免把过期证据用于后续已变化的数据。无法恢复或无法验证时阻止回收。
11. **分类与处置。** 数据分为需保存成果、经明确规则可重建或可丢弃的内容、用途未明内容。项目规则与用户分类决定处置范围；仅有忽略规则或目录名不足以授权丢弃。完成备份不改变用途未明内容的处置权限。
12. **保留契约。** Agent 申请需要理由和到期时间或可验证解除条件；用户可决定长期保留。条件不明确时不能假定已解除。解除只移除这项阻碍，其他检查照常执行。
13. **依赖保护。** 所属线程和依赖关系分别判断。跨线程接续通过独立派生副本完成；无法确认对其他副本或快照的影响时保留资源。PP 不直接删除后端的底层存储目录。
14. **持续协调与重试。** 复用 ticker 和恢复流程持续核对已完成线程仍待处理的资源，补足仅在首次 resolve 时尝试的缺口。重启、条件变化和失败重试均重新核对身份与成果；重复或并行触发不得造成越权操作、遗漏保护条件或错误成功状态。占用探测、文件检查或后端查询失败不能解释为安全无阻碍。
15. **可见结果与通知。** 查询和看板能够从线程定位其各项资源、实际后端、阶段、阻碍及可采取的操作。持续异常通知去重，原因变化应可见；去重不删除真实待处理记录。具体界面布局和重试节奏留给实现设计。
16. **统一管理入口与外部资源。** 更新 Agent 工作规则，要求 PP 任务相关的实验和快照通过 PP 申请。绕过入口创建的资源发现后标为待确认，仅明确接管后纳管。该入口是 PP 的管理契约，不承诺将 Agent 的通用 shell 变成无法绕过的沙箱。
17. **复用规则。** 默认不继承未知忽略文件、凭据或本机状态；项目声明可复用范围及有效性要求。复用后写入相互隔离，失效或无法判断时重新验证或重建，不选择不安全复用来保证速度。
18. **资源压力。** 预检资源预算和空间警戒线；触发后阻止新增副本和快照，并显示原因及处理选项。已有任务尽量继续，只有满足原有检查的资源可回收。不得自动解除保留或降低保护标准。
19. **支持与回退。** 首批限定本机 macOS 和实际验证过的版本。其他平台或远程继续走 Git worktree。OVNFS 优先策略仅在尚未创建资源的预检失败阶段允许可见回退；显式 OVNFS 失败直接报错。已创建资源只恢复原后端环境。
20. **分阶段接入。** 先完成共同生命周期，再交付本机 OVNFS 可选闭环、历史核对、故障验收与同任务比较，最后按证据逐步调整默认。旧线程不原地转换后端，历史数据不因线程已完成而批量删除。
21. **默认切换门槛。** 可靠性与收益分别验收。具体支持版本、预算数值、空间警戒线、重试节奏和收益阈值需要在对应阶段测量、记录并落实为可复核配置或验收条件；这些值未确定、验证未通过时，默认切换阶段仍被阻塞。不得由实现者自行宣称未测得的收益。
22. **OVNFS 副本只通过显式命令删除。** `pp thread delete-checkout <slug> <id> [--resource NAME]` 每次只处理已完成线程的一项已登记本机 OVNFS checkout，默认主副本。Agent 接到清理指示后可以非交互执行。`resolve`、`thread cleanup`、ticker 和 `sweep` 永远不调用这个删除；未接管的历史 OVNFS 副本及其声明丢弃项也不自动清理。按原有契约核对身份、挂载、保留、Agent 归档、成果、占用和依赖；固定版本的非强制 `rm` 按名字操作，最后一次检查和删除之间仍有外部操作的竞态。PP 不以快照或 base 为删除目标，也不操作底层存储目录；后端可自行回收无引用存储。未确认成功时报告状态，不自动重发 `rm`。

## Testing Decisions

### 已确认的测试边界

优先使用现有最高层可运行边界：**PP CLI 与 ticker 工作流**。从这些入口创建、查询、完成、恢复和回收资源，断言用户可见状态、保存后的文件与提交、实际剩余资源以及禁止发生的副作用。现有看板通过同一查询契约呈现结果，界面验收补充验证原因与后端是否可见，不为内部函数单独增加一套测试入口。

现有先例包括：隔离 Git 仓库与工作副本、CLI 子进程调用、模拟 Paseo WebSocket daemon、OVNFS 命令替身、GitHub 命令替身，以及单次 ticker 和完整 ticker 子进程测试。延续这些方式验证线程生命周期、清理、后端适配、成果保存和看板读取；不根据某个私有函数被调用几次判定正确。

自动化需要可重复控制中断、部分成功、查询失败和占用。优先在上述公共工作流的既有依赖替身处注入故障，而不是为测试导出实现细节。替身的成功返回不能替代真实挂载、COW 隔离或依赖安全证据。

另在本机 macOS 上，使用固定的候选 OVNFS 版本和隔离目录运行同类真实后端验收。只有真实后端通过身份、挂载、隔离、派生、快照依赖及中断恢复检查，才视作 OVNFS 闭环验收通过。

以下验收不对用户现有线程、凭据或未登记历史目录执行删除，也不通过强杀真实用户进程制造故障。

### 行为验收矩阵

| 编号 | 输入或事件 | 必须观察到的结果 |
| --- | --- | --- |
| AC01 | 一个线程申请主副本、实验副本和快照 | 所有资源有可查询归属；创建前已有可恢复意图记录；不存在无法定位的成功副本。 |
| AC02 | 从已登记资源跨线程派生，两个线程分别写入 | 派生副本归属新线程，写入互不改变对方环境；来源和依赖可查询。 |
| AC03 | 从包含未提交修改的源目录普通创建 | 使用记录的明确提交版本；源目录及其未提交修改不变；新副本不隐式包含这些修改。 |
| AC04 | 显式继承源目录尚未提交的修改 | 带入内容和来源可解释；起点能够独立恢复；之后产生的变化可与起点区分。 |
| AC05 | 副本创建成功后 Agent 启动失败或进程中断 | 显示真实资源与未完成操作；后续可恢复或回收；重试不产生失去管理的额外副本。 |
| AC06 | 重启后挂载缺失、路径被替换或身份查询失败 | Agent 等待或报错；不在源仓库、替换目录或其他后端运行；不删除身份未确认的路径。 |
| AC07 | 线程完成且各项检查通过 | 自动分别归档并回收合格资源；无需逐项确认；实际结果与对外状态一致。OVNFS checkout 只按 AC29 显式删除。 |
| AC08 | 代码成果仅在副本内、报告复制损坏或归档验证失败 | 回收被阻止并显示具体缺失证据；修复后可再次核对；不能仅凭口头报告或复制返回成功删除。 |
| AC09 | 提交、报告与登记产物在副本外保存并验证 | 隔离环境中移除原副本后仍能恢复被声明保存的成果；无需强制要求上传或合并。 |
| AC10 | 只有依赖原副本的快照，或快照独立性无法确认 | 不视作独立成果保存证明；回收不会破坏其承诺保存的数据。 |
| AC11 | 存在独有提交、未提交修改、未知文件或未知忽略文件 | 未明确保存或处置前阻止回收；归档完成也不自动授予未知内容的删除权限。 |
| AC12 | 内容仅因名字为 TEMP、node_modules 或命中 Git 忽略规则 | 不自动判定可丢弃；明确且适用的分类规则满足后才按规则处理。 |
| AC13 | Agent 申请无条件长期保留、有效短期保留，以及用户长期保留 | Agent 请求必须补足理由与期限或条件；有效保留阻止回收；只有用户可决定长期保留。 |
| AC14 | 保留到期但仍有占用或独有数据 | 仅解除相应保留，其他阻碍保留；不得直接删除；条件满足后自动继续。 |
| AC15 | 多资源线程完成，其中一项被进程占用 | 符合条件的先回收；占用项继续存在且线程可保持完成；进程退出后重试，不强杀。 |
| AC16 | 其他线程或有效快照仍依赖底层数据，或依赖检查失败 | 不破坏依赖方；不直接删除底层目录；无法确认安全时显示阻碍。 |
| AC17 | 后端回收失败、占用探测失败或操作中断后重启 | 真实失败或未知状态可见，不记为已回收；恢复后重新确认身份和检查；不升级为强制操作。 |
| AC18 | ticker 多次运行或命令与 ticker 重复触发同一资源操作 | 不重复破坏资源，不绕过检查，不错误成功；持续相同异常不反复轰炸通知。 |
| AC19 | 发现未知环境或显式接管外部环境 | 未接管时仅显示待确认且不删除；接管后有明确归属、身份与来源记录，再按规则管理。 |
| AC20 | 项目声明缓存可复用，同时源目录含未知忽略数据及本机凭据 | 只继承允许范围；各副本写入隔离；测试使用虚构凭据，未知内容不隐式带入。 |
| AC21 | 影响缓存有效性的输入发生变化或有效性检查失败 | 重新验证或重建；不为了复用而使用已失效或无法确认的环境。 |
| AC22 | 资源预算或空间警戒线被触发 | 拒绝新增副本与快照并显示原因；不主动终止已有任务，不强删、不解除保留。 |
| AC23 | 默认优先策略预检失败、显式 OVNFS 失败、创建后故障 | 分别验证可见的创建前回退、直接报错、只恢复原资源；不得混淆三种情形。 |
| AC24 | 已有 Git worktree、OVNFS 线程和未登记遗留环境 | 不原地换后端，不依据 resolved 状态批量删除；核对、认领和保存后逐项进入管理。 |
| AC25 | 非首批支持平台或远程机器创建线程 | 继续使用 Git worktree 或对显式不支持请求报错，不能声称通过本机验证就支持所有平台。 |
| AC26 | 从查询入口及看板查看已完成但待处理的线程 | 看到各项资源、实际后端、阶段、原因和可采取的操作；不会把资源保留显示为全部回收完成。 |
| AC27 | 固定版本的真实 OVNFS 完整场景与受控中断 | 验证真实挂载、私有 Git 状态、隔离写入、派生、快照依赖、恢复及回收；替身测试通过不算此项通过。 |
| AC28 | OVNFS 与 Git worktree 使用相同任务和可复核环境 | 记录环境准备时间、执行表现与存储测量方法；区分逻辑大小和实际物理占用；未设门槛或未通过时默认仍不切换。 |
| AC29 | Agent 接到清理指示后非交互运行 `pp thread delete-checkout <slug> <id> [--resource NAME]` | 只删除满足各项检查的一个已登记本机 OVNFS checkout；不删除快照、base 或旧线程的未接管资源。只有在确认注册表和文件系统均不存在该 checkout 且挂载正常时才记为已回收。失败或不确定时报告原因，不自动重试；再次显式运行可确认先前已删除，不重发不确定的 `rm`。`resolve`、`thread cleanup`、ticker、`sweep` 和看板均不触发删除。 |

AC08–AC19 的保护条件仍适用于 OVNFS；其中的回收推进或重试不触发 OVNFS 删除，删除始终遵守 AC29。

### 测量与默认切换验收

基准记录任务、代码基线、允许复用内容、后端及版本、机器条件、测量方法和失败情况。对照使用相同任务输入，分别说明环境准备与执行时间，避免把依赖已预热的情况误作所有任务的普遍收益。

存储报告必须说明统计的是逻辑目录大小、分配量还是能够验证的物理占用。不能累加挂载视图与底层存储，也不能将可能共享 APFS extents 的目录大小直接称为可回收空间。无法准确测量的指标明确标为未知，不推算成已证明收益。

生命周期验收失败时停止默认切换；生命周期通过但收益或量化门槛未形成时维持可选。具体量化门槛待取得可复核测量后确定，本规格不编造数值。

## Out of Scope

- 本规格不授权立刻将 OVNFS 设为默认、移除 Git worktree，或将 COW 的潜在优势写成既有性能结论。
- 首批不实现远程机器、Linux 或 Windows 的 OVNFS 支持，也不默认扩展到未经验证的版本。
- 不原地迁移现有工作副本，不批量删除 resolved 线程目录，不自动接管外部资源。
- 不将来源未明内容、未知忽略文件或凭据默认视作可复用或可丢弃数据。
- 不设计强制删除、自动强杀用户进程、绕过后端删除共享存储，或“重试多次后降低保护等级”的机制。
- 不将所有执行现场永久归档；需要现场的实验通过保留或登记成果处理。
- 不在本规格固定未经验证的预算、版本范围、时间间隔或性能阈值；对应阶段必须补足证据，不能据此跳过门槛。
- 不顺带重做 Tasks 面板的自动派工、模型路由、通知通道或其他无关功能。
- 不因生成规格而合并、关闭或修改回滚 PR，不停止现有会话、ticker 或 OVNFS daemon，不卸载软件。
- 不将 Agent 的通用 shell 变为强制资源沙箱；对绕过 PP 的资源先发现、显示并要求明确接管。

## Further Notes

### 阶段与退出条件

| 阶段 | 交付重点 | 完成条件 |
| --- | --- | --- |
| A：共同生命周期 | 资源登记、身份、归属、阶段与阻碍、成果证明、保留、自动重试 | 共同的外部行为验收通过，既有 Git worktree 行为得到保护；默认不切换。 |
| B：本机 OVNFS 闭环 | 验证版本；主副本、实验、快照、派生、复用规则、恢复和回收 | 替身覆盖故障分支，真实后端完整验收通过；保持可选。 |
| C：历史核对 | 识别、展示、认领和逐项纳管旧资源 | 不改变原后端；独有数据、有效保留和其他线程依赖受保护；不要求批量清空历史现场。 |
| D：收益验证 | 同任务准备、执行及存储对照 | 可复核数据和量化门槛形成，不能确认的指标标明未知。 |
| E：默认提升 | 按已验证范围逐步调整新建资源策略 | 可靠性与收益两类门槛均通过，创建前回退与显式指定语义通过；旧线程继续使用原环境。 |

各阶段可分别形成实施任务；它们不意味着本规格发布后即可直接执行生产迁移。最终是否移除 Git worktree 仍依据扩大支持范围后的验证结果决定。
